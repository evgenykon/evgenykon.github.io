My Books 0.4.6 — a Windows build, encrypted vaults and self-updates

Five days ago I wrote about My Books as an FB2 reader with one Kotlin core and two shells — Android and macOS. Since then the repository took 31 commits and the app turned into three platforms with a synced, encrypted library. Same core, same Block model, same reading position — only now the position you saved on the phone also shows up on the Mac and on Windows.

Repo: github.com/evgenykon/my-books · Releases: v0.4.6

Windows: the third shell

desktopApp/ is Compose Multiplatform on the JVM, with shared compiled to a JVM target. The reader is not a port of the Android UI — it is a desktop reader: the text column is width-capped so lines do not run across a 27-inch screen, navigation is ← →, PgUp/PgDn, space, Home/End and the mouse wheel, Ctrl + +/- changes the font size, and contents, notes and settings are side panels instead of phone bottom sheets.

Import works three ways: drag a file into the window, Ctrl+O, or straight from the command line (MyBooks.exe book.fb2) — the installer registers the .fb2 association, so double-clicking a book opens it. Library lives in %LOCALAPPDATA%\MyBooks\library as plain JSON plus one .fb2 per book.

Two packaging details worth the effort: the MSI bundles its own JRE (96 MB, no “install Java first”), and MyBooks.exe and the MSI are signed with a self-signed certificate. Windows still says “unknown publisher” until you install mybooks.cer from the release into Trusted Root Certification Authorities — after that the publisher is shown. Only a paid OV/EV certificate removes SmartScreen entirely; I am not buying one for a personal reader.

Encrypted vaults in git branches

The part I actually wanted: one library across three devices without a server. A vault is a branch of a private GitHub repository — one branch, one vault.

  • vault.enc holds the manifest (books, notes, reading progress, settings) and books/<id>.enc holds one encrypted blob per book, so adding a book does not rewrite the whole library.
  • Crypto: PBKDF2-HMAC-SHA256, 200 000 iterations, into AES-256-GCM. The file stores only the KDF envelope, salt, nonce and ciphertext — the password never leaves the device.
  • The GitHub token and each vault’s password live in the OS secret store: DPAPI on Windows, Android Keystore (EncryptedSharedPreferences), Keychain on macOS. The password is asked once, when the vault is created.
  • Any change (book, note, progress, settings) is pushed to the active branch ~1.5 s later; there is also an explicit sync button. Opening a vault on a new device pulls the books down, applies notes, progress and settings, and does not duplicate what is already there. Startup now syncs both ways.

Vault names are branch names: lowercase latin, digits and -, 1–40 characters, with main, test, windows and friends reserved.

Self-updates on Android and Windows

Both apps check /releases/latest themselves. Android shows a banner, downloads the APK through a FileProvider and hands it to the system installer; there is also a manual “Check for updates” in settings. Windows shows a strip above the library, downloads the MSI, quits, installs and relaunches the app.

The Windows half has a trap that cost me a release: Windows Installer compares product versions, not files, so an MSI with the same version just installs the same product again. version.txt now drives packageVersion = 1.0.N, where N is the patch number — every release is a real upgrade.

The APK is signed with my own key and installed outside Google Play, so Play Protect warns about an “unsafe app”. That is normal for sideloading: “More details” → “Install anyway”. Builds come from GitHub Actions in this repository, nothing is republished anywhere else.

Reader work

  • Footnotes: markers in the text are now clickable and show the note itself — the FB2 name="notes" body I already moved to the back of the book finally became usable.
  • Quotes: adding a note stores only the selected text, not the whole paragraph; text that is quoted somewhere in your notes gets a dotted underline, so you can see what you have already marked.
  • Fonts: four Cyrillic families bundled (Alegreya, Merriweather, PT Serif, Spectral), each with regular, italic, bold and bold-italic — no dependency on what the system happens to have.
  • Fixes along the way: page height had to exclude the toolbar (otherwise the last line of every page was cut), the settings button opened the wrong sheet on Android, and space in the note editor used to dismiss it instead of typing a space.

CI

Every platform is built on GitHub Actions: Android (tests + APK), macOS (Kotlin/Native arm64+x64 → Shared.xcframework → swift build), Windows (:shared:desktopTest, portable zip with embedded JRE, MSI). The release workflow publishes assets even when one platform fails, and keeps the macOS compiler log as a public artifact — the same trick as the deploy here: a build you cannot read the log of is a build you cannot trust.

No local Gradle builds at all. :desktopApp:snapshot renders UI screenshots without opening a window, which is how the Windows layout gets checked in CI.

My Books — one FB2 core, two platforms: Android and macOS

I read a lot of FB2 — it is basically the default format of every Russian e-library — and every reader app I tried either ignored my notes, lost the reading position after an update, or was a web wrapper around something else. So I wrote my own: My Books, an FB2 reader for Android and macOS with a single shared core.

Repo: github.com/evgenykon/my-books

The idea: one parser, not two

The interesting part is not the UI. It is that both apps read a book through the same code. The book is parsed once into a flat list of blocks (Block), and the reading position is simply (block index, character offset). No DOM, no attributed strings in the core, no per-platform parsing quirks — a position saved on the phone opens at the same word on the Mac, and the percentage is computed in one place (ReadingProgress).

shared/      Kotlin Multiplatform core: FB2 parser, book model, reading progress
androidApp/  Kotlin + Jetpack Compose
macos/       SwiftUI + CoreText (SwiftPM, core as Shared.xcframework)

What the core does

  • Xml.kt — a fault-tolerant XML reader with zero dependencies, because real FB2 files from libraries are broken far more often than you would like. Encodings: UTF-8, windows-1251, KOI8-R, Latin-1, UTF-16, plus named entities (&nbsp;, &mdash;, …).
  • Fb2Parser.kt — title info (name, authors, annotation, cover), the body (headings, paragraphs, epigraphs, poems, images), a table of contents built from section/title, and the name="notes" body moved to the back of the book as footnotes.
  • Model.kt — Book, Block, TocEntry, Position, ReadingProgress.
  • Tests in shared/src/commonTest: parsing, TOC, block indices, progress, cp1251 and UTF-8-with-BOM decoding.

Android

Import via SAF (no storage permissions at all), a library with progress, deleting a book together with its notes. The reader paginates by the real layout of the text through TextMeasurer, shows book / author / “page N of M” / percent in the header, and has its own text toolbar for Copy and Add note — the quote is taken straight from the selection.

macOS

Import via fileImporter, pagination through CTFramesetter, page navigation with arrows, space or swipe. Selection is native (textSelection(.enabled) + ⌘C), plus a paragraph context menu with “Copy paragraph” and “Add note”. Font family, size, line spacing, margins, theme (light / sepia / dark) and justification work the same way on both platforms.

Builds

No local Gradle builds — both platforms are built in GitHub Actions:

  • Android — :shared:testDebugUnitTest + :androidApp:assembleDebug, the APK lands in the mybooks-debug-apk artifact;
  • macOS — Kotlin/Native frameworks are linked into Shared.xcframework, then SwiftPM builds the app.

That is the whole point of the architecture: the risky, bug-prone half (parsing, positions, progress) is one Kotlin module with tests, and both UIs are thin shells over it.

Flat Earth: arguments and counter-arguments, side by side

Every argument with a flat-earther ends in the same place: the same twenty claims, recycled, and a Wikipedia link nobody opens. So instead of arguing I made a site that puts the claim and the rebuttal next to each other — Плоская Земля: доводы и контр-доводы.

Site: evgenykon.github.io/flat-earth · Code: github.com/evgenykon/flat-earth

Two sides, two reading modes

  • The light side (/light/) — the flat-earther claims. Open a claim and the scientific counter-arguments are right there, no extra clicks.
  • The dark side (/dark/) — the attacks on science taken from the primary sources, quoted verbatim with attribution. The rebuttals are hidden until you press “I want the counter-arguments” at the top of the page: you read the argument the way its author meant it, and only then flip the switch.

The dark side is built from three books — Rowbotham, Zetetic Astronomy (1865); Carpenter, One Hundred Proofs That the Earth Is Not a Globe (1885); Dubay, 200 Proofs Earth is Not a Spinning Ball (2014). The texts are public domain, so a script parses them, splits them into numbered proofs, groups them by topic and attaches topic-specific counter-arguments (scripts/generate-dark.mjs), then translates everything to Russian through a public Translate endpoint (scripts/translate-dark.mjs). Hand-edited files are never touched by the scripts.

Content is just markdown

Adding an argument is one file: frontmatter (title, claim, argument, category, order) plus the counter-arguments in the body. git push → GitHub Actions builds → the argument is live. No CMS, no database.

The site itself is Astro + Tailwind with a custom sand palette (no default theme), deployed to GitHub Pages from main.

Why bother

Not to convert anyone — the goal is narrower and more useful: to show why each claim fails, with the original wording in front of you. It is also a decent exercise in reading primary sources: the 19th-century proofs are a fascinating mix of geometry, bad measurements and total confidence.

Solo Traveler's Guide — an Android audio guide that talks when you arrive

Walking tours have one annoying property: you look at the phone instead of the city. So I built an Android audio guide that does the opposite — you walk, and when you enter a point’s zone it starts telling you about the place, screen off, hands free.

Site: evgenykon.github.io/travel-guide · Code: github.com/evgenykon/travel-guide

How it works

  • Map — MapLibre with OpenFreeMap vector tiles. Tap a point for a card with its name, OSM object, coordinates and elevation; long-press the map to create a new point, or drop one at your current location.
  • 10-metre geofences — a foreground service with a persistent notification watches your position and narrates the description the moment you step into the zone, including with the screen off. Each point is narrated once; re-play it from History. Before tracking starts a checklist verifies permissions, background location, notifications, unrestricted battery — and autostart/battery settings on Xiaomi/MIUI, with deep links straight into the right settings screen.
  • Voice — Yandex SpeechKit, selectable voices and speed, audio cached on the device.
  • Descriptions — written by hand, or generated through OpenRouter. The app resolves the OSM object, the Nominatim address, the city and the country first and injects them into the prompt, so the model doesn’t confuse two places with the same name. Coordinates are never spoken out loud. The prompt template is editable.
  • Routes, history, import/export — routes with their own points, zone and playback history, JSON export/import that merges by name and coordinates without duplicates.

Everything lives on the device: Room for points/routes/history, DataStore for settings, EncryptedSharedPreferences for keys. After a reinstall the content comes back from Android auto-backup — the keys deliberately don’t.

A route editor without a backend

The browser editor is a plain page: the same MapLibre map, drag points, set radius, resolve addresses, generate descriptions through OpenRouter, import/export the app’s own BackupFile format. The API key stays in page memory (or, on request, in the tab’s sessionStorage) — there is no server to leak it.

CI

Push to main → unit tests, lint, debug APK as an artifact and a rolling dev-latest pre-release; a vX.Y.Z tag → signed release APK and a GitHub Release. The site is published from site/ by a separate workflow.

Install: releases (APK, Android 8.0+; SpeechKit and OpenRouter bill you per use, the app itself is free).

Self Testing — static site for self-check quizzes

A static site with quizzes on different topics, built as a Nuxt 4 SPA and deployed to GitHub Pages.

Quizzes are grouped by topic with a sidebar index; one page = one quiz. Three question types are supported: single choice, multiple choice, and text input. Questions, answers, and explanations support markdown, images, and LaTeX formulas (KaTeX, rendered at build time).

Each quiz can have a timer for the whole test or per question, with a progress bar on top. Scoring is 0/1/2, and the results page breaks down every answer. Questions and options are shuffled on every run, and attempts are stored locally: the Stats page shows per-quiz history charts with a reset button. The “I don’t know” button flags a question, and flagged questions are collected on a review page with correct answers and explanations.

Quiz sources are plain markdown files (content/tests/*.md), and the build script parses them, renders KaTeX/markdown to HTML, and obfuscates the payload (XOR + Base64 with a random per-build key) before Nuxt generates static pages. There’s also an LLM prompt that converts any file or web page into a quiz in the supported format.

Everything runs inside Docker (make install, make build, make test), and pushes to main deploy to GitHub Pages via GitHub Actions.

Stack: Nuxt 4.6, TypeScript, Tailwind CSS 4, markdown-it, KaTeX, Vitest, Docker Compose.

Try it: https://evgenykon.github.io/self-testing/

Source: https://github.com/evgenykon/self-testing

Small tools for use in your presentations LaTeX → PNG converter + Graph of a function

A single-page tool for converting LaTeX formulas to PNG right in the browser. No backend: rendering is done by MathJax 3 (SVG), after which the image is transferred to a <canvas> and saved as PNG.

Features: formula input with quick template buttons (fraction, root, sum, integral, Greek letters), text and background color pickers including a fully transparent background (alpha channel), font size setting, auto or fit-to-size image dimensions, live preview and one-click download, dark theme (Tailwind CSS).

The second page (plot.html) renders function graphs on Plotly.js with native LaTeX in the legend: the formula is parsed into a JS function by the @cortex-js/compute-engine engine, supports constant parameters (a=1, b=2, c=-3), automap Y toggle, legend/axis/grid styling, transparent background, and discontinuity splitting for \tan(x) and 1/x.

The third page (draw.html) is a drawing pad: pen, marker, soft brush and eraser tools, brush size and color settings, canvas size, undo and clear, transparent background, and PNG export at ×1–×4 scale.

Stack: MathJax 3, Plotly.js, compute-engine, Tailwind CSS, GitHub Pages.

Escape Map Game — reach the shelter before the blast

A browser-based escape map game (MapLibre + OpenFreeMap tiles) where the player must reach a shelter before a blast at a random epicenter.

The game uses geolocation, fetches roads and buildings from the Overpass API within a ~15 km radius, builds a road graph, and places a single shelter 1.5–2 km from the epicenter. Some cars can be driven (press E), locked cars can be hacked (hold E). Vehicles have fuel and physics (drift, off-road penalty). Refuel at fuel stations.

Controls: WASD — movement, Shift — run, mouse — camera rotation, E — interact (enter/exit car, start/cancel hack), M — cycle map modes (follow, overview, tactical). HUD shows countdown timer, scenario SMS, shelter compass, and fuel gauge.

At the moment of the explosion: if inside a shelter — win, otherwise — lose.

Stack: TypeScript, Vite 5, Vue 3 (Composition API), Pinia, MapLibre GL JS, Turf.js, Docker.

Play: https://evgenykon.github.io/escape-map-game/ Source: https://github.com/evgenykon/escape-map-game

Alert data to sound mapping

Real-time sonification of ZTF(and LSST in future) alerts, designed for accessibility.

Each night, Observatory will discover hundreds of thousands of transient events. This app turns that stream into spatial audio: waveform encodes object type, pitch encodes redshift, volume encodes magnitude, and 3D panning encodes sky position.

Visually impaired scientists can classify events by ear. Sighted researchers can monitor the stream while reading or writing. Anyone can feel the rhythm of the transient sky.

18 object classes, 8 sound palettes, Web Audio API, Vue 3, Bun + KafkaJS. Docker + Hugging Face Spaces + GitHub Pages.

Life (fork) v2 — civilization survival strategy on a resource map

I’ve released version 2 of my browser-based strategy game — Life (fork).

Try it live: evgenykon.github.io/life-game-fork

What is Life (fork)

Multiple races start on a 20×20 map with one base and an initial supply of meal, water, and material. Each cycle (1 sec) races expand by capturing adjacent cells, build factories on resource tiles, and attack each other. Last race standing wins. Despite the name, it has nothing to do with Conway’s Game of Life — just a similar theme of cellular automata.

Cell types

  • base — race’s home. Losing the last one means extinction.
  • resource — resource tiles: field (meal), forest (meal + material), rock (material), mineral (water + material), swamp (meal + water), snow (water), water (water), dirt and sand (empty).
  • fabric — a factory built on a tile, harvests its resource every cycle.

Turn sequence

Each cycle: territory capture → attack → factory progress → new action selection (capture/attack/build) → resource harvest → upkeep (−2 meal, −1 water, −1 material) → deficit (lose a tile) → resource depletion → recovery.

Combat takes 5 cycles (−1 material/cycle). Attack priority: bases > factories > resource value. A surrounded tile is captured in 1 cycle (liberation).

Race strategy

Each race gets random weights for expansion / building / war (sum = 100%). Priorities are redistributed when resources run low. If a race is attacked, its war priority immediately increases by 20.

UI

Built with Effus UI — my own Tailwind Template for Vue.js available on npm.

What’s new in v2

  • Overhauled resource and depletion mechanics
  • Adaptive race priority system
  • Liberation mechanic (fast capture of surrounded tiles)
  • Improved AI with deficit-driven factory placement
  • Balance modal for tuning numeric constants

Three Body Problem — interactive simulation and educational guide

I’ve launched a new pet project — an interactive web application exploring the Three-Body Problem in celestial mechanics.

Try it live: evgenykon.github.io/three-body-problem

Built with Nuxt 4, Vue 3 and TypeScript, the app combines a real-time 2D physics engine with an educational guide covering 300+ years of research — from Newton’s classical formulation (1687) to modern machine learning approaches.

Interactive Simulation

  • Three numerical integrators: Euler, RK4, Velocity-Verlet
  • Adjustable gravitational constant, time step, and softening parameter
  • Collision detection, trajectory prediction, and trail visualization
  • Body selection with position/velocity picking, zoom, and grid overlay
  • Dark theme with custom CSS, no external UI framework

Periodic Orbits Catalog

10 precalculated orbit families (Figure-8, Butterfly I, Bumblebee, Moth I–III, Goggles, Dragonfly, Yarn, Yin-Yang I) generated offline with Velocity-Verlet at high precision and replayed at runtime for perfect stability.

Educational Content

9 in-depth pages covering Newton’s Law, Euler’s restricted solution, Lagrange points L1–L5, Poincaré chaos theory, Sundman’s convergent series, numerical integration methods, homological classification, and ML-based orbit prediction.

Tech

  • Framework: Nuxt 4 with Vue 3, TypeScript
  • Physics: Custom 2D N-body engine
  • Rendering: HTML5 Canvas
  • Math: KaTeX for LaTeX equations
  • i18n: Full English and Russian translations
  • Containerization: Docker Compose
  • Deploy: GitHub Actions → GitHub Pages

Frontend framework research

Last week in my current job was definitely important for company future. And my personal responsibility was to find a way for comparing a lot of today popular frontend frameworks, and to make a choise for one.

First of all I looked at Vue ecosystem because our current FW is Vue2. We using it not for whole project but for new features only. So we merge it together with old legacy codebase.

And I think that newest Vue and vue-based frameworks is better way for my team. It should be easest entry threshold of all. It is one of 3 popular FW at present moment. And Vue-team had made last version (I mean Composition API) very close to React. So our new team members, which has already been experienced with React, get an easy and clear way to learn our codebase if it would base on Vue 3.

When we talk about expectations of new FW with my team, we have found some points. It would be nice if our new FW have: latest Vue version at the moment, large native component library with usable gallery and docs, flexible and adaptive UI and an access to SCSS variables to set up custom corporate styles.

I have founded about 10 different FW based on Vue, and have made clear setup of each one according to instructions. I can say, that not all of their setup actions has finished correcly. May be that was my fault, but I’m sure this is very important thing for opensource projects is that other guys (which do same research as me) will make same mistakes. Thats why you (fw vendors) need to reproduce your installation instructions after every release and should try to do it as easy as you can.

Here is list of my top 3 Vue frameworks that I’ve looked at:

    1. Quasar: Best of the best. I’ve already known about that FW, and even have some repos with it (don’t remember exactly how much). I’d found preinstalled Vue3, TS, Vite, Pinia, ESLint, Material UI, vue-router and own client for build operations. About 30 minutes for docs learning, repeat instructions and fix some problem with routing.
    1. Core UI: Nice own component style. Problems with preinstalled prettier (found and errors immediately when I type some tags with CR line brakes). I had found a solution but there a couple of my time has been wasted. Also there is no preinstalled storage inside (but Jest+Cypress).
    1. Element Plus (ready boilerplate repo). Beautifully designed gallery of components, no problems with setup. But I had some problems with styles tuning, and had found unexpectable component behaviour when doing a full-clickable ‘card’.

  | Pinia store      ^

  | Vue3           I | Vue3             T | Vue3

Some fw I refused by reasons.

  • Nuxt 3: what should I do with version based on Vue3? It is very scarce documentation, just concerning migraion from Vue2. No components, no popular boilerplates.
  • Nuxt 2: just with Vue 2.
  • Vuetify: vue version in repo right now: v2.6.7
  • Gridsome: I love it but jamstack is not for our project. Sad. Other founded fw is:
  • Element Plus + Nuxt (try to install EP to empty Nuxt project manually - failed)
  • Vue Material (just beta right now)
  • Nuxt 3 + BootstrapVue (manual too)

So, just want to say at least: that was an example of how developer(s) make choise for new tools. That tools will be together with team for few next years, and there are a lot of small but important things that influence to the choice.
